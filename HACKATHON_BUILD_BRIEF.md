# Hackathon Build Brief: RainRoute

**Working name:** RainRoute  
**Tagline:** One policy. Any rail. Safe spending for autonomous agents.  
**Target:** Raingentic Commerce Hackathon, August 8–9, 2026.

---

## 1. Product

RainRoute is a procurement agent that can buy from both machine-native and ordinary merchants while remaining inside a human-approved budget.

- Monad x402 pays APIs, datasets, and agent services.
- Rain scoped cards pay legacy card merchants.
- Rain payments can later add stablecoin/fiat payouts.
- ERC-8004 can identify and rank agent vendors.
- A deterministic policy engine controls every transaction.
- Monad stores policy and receipt hashes; private details remain offchain.

### Demo story

“Find the best market-research source under $25, buy the report, then subscribe to the selected analytics tool for no more than $80. Only software/data merchants. Finish before 5 PM.”

The agent:

1. Converts request into a structured plan.
2. Checks total and per-step policy.
3. Discovers two data services.
4. Pays $0.001 through x402 on Monad for a pricing/reputation result.
5. Chooses a vendor.
6. Creates a Rain scoped card limited to the vendor, software/data MCC, $80, one use, 15-minute expiry.
7. Completes the allowed sandbox purchase.
8. Attempts a $200 unrelated transaction; Rain/policy blocks it.
9. Retires the card.
10. Shows receipts, policy decisions, and final budget.

### Why this can win

- Rain is the center of real-world execution.
- Agent behavior is real, not a chatbot wrapper.
- The blocked transaction visibly proves control.
- Monad solves micropayment, discovery, and audit needs.
- Story is understandable in under 30 seconds.
- Architecture has an obvious enterprise path after the hackathon.

## 2. Scope

### Must ship

- Natural-language procurement request.
- Structured plan generated by model or deterministic sample agent.
- Policy editor: total budget, merchant/recipient, MCC, expiry, max transactions.
- Policy simulation before spend.
- One real Rain sandbox operation.
- Rain scoped-card lifecycle: issue, display masked metadata, freeze/retire.
- One permitted payment event.
- One denied payment event.
- One x402 payment on Monad testnet.
- Live event timeline.
- Receipt/reconciliation screen.
- Secrets kept server-side.
- Clear fallback mode when either external service is unavailable.

### Should ship

- ERC-8004 vendor identity/reputation lookup.
- Hash of approved policy written to Monad.
- Hash of final receipt written to Monad.
- Human approval above a threshold.
- Webhook signature verification and duplicate suppression.
- Rail-router decision explanation.

### Do not build during hackathon

- Full accounting platform.
- Production KYC UI.
- Real-money mainnet purchasing unless sponsors explicitly support it.
- General browser-use agent.
- Multi-country payroll.
- Custom token.
- DAO governance.
- Fully decentralized reputation.
- More than two merchant/payment paths.
- Card-data handling outside Rain-approved components.

## 4. Architecture

```text
Next.js UI
   |
API / Agent Orchestrator
   |------ LLM planner -> JSON schema validation
   |------ Deterministic policy engine
   |------ Rail router
              |------ Rain adapter
              |          |-- scoped cards
              |          |-- payments/transactions
              |          \-- verified webhooks
              |
              |------ Monad adapter
                         |-- x402 client
                         |-- policy/receipt registry
                         \-- ERC-8004 lookup
   |
Postgres/SQLite
   |-- missions
   |-- policies
   |-- payment intents
   |-- events/idempotency keys
   \-- offchain receipt data
```

### Recommended stack

- Next.js + TypeScript.
- Server-side route handlers or a small Node service.
- `zod` for agent-plan and policy validation.
- `viem` 2.40.0 or later for Monad.
- x402 v2 packages from the current Monad guide.
- SQLite for fastest local build; Postgres if starter already provides it.
- Server-sent events for timeline updates; WebSockets unnecessary.
- Playwright for one golden-path browser test.

Do not add an agent framework unless it saves time. A small state machine is safer and easier to demo.

## 6. Agent contract

The model may propose actions. It cannot execute arbitrary tools.

```ts
const AgentPlanSchema = z.object({
  summary: z.string().max(500),
  steps: z.array(z.object({
    id: z.string(),
    purpose: z.string(),
    recipient: z.string(),
    merchant: z.string().optional(),
    amountMinor: z.string().regex(/^\d+$/),
    currency: z.literal("USD"),
    preferredRail: z.enum(["rain_card", "rain_payment", "x402_monad"]),
    needsHumanApproval: z.boolean(),
  })).min(1).max(5),
});
```

After parsing:

1. Convert numeric strings to `bigint`.
2. Recompute totals; never trust model arithmetic.
3. Normalize merchant and recipient identifiers.
4. Run deterministic policy checks.
5. Require explicit approval where applicable.
6. Build a server-side payment intent.
7. Execute only the intent, never free-form model output.

## 7. Policy engine

### Decision order

```text
mission active?
-> policy unexpired?
-> rail allowed?
-> recipient/merchant allowed?
-> MCC allowed?
-> transaction count available?
-> per-payment amount allowed?
-> aggregate exposure allowed?
-> human approval present if needed?
-> execute
```

### Return reason codes

- `POLICY_OK`
- `MISSION_INACTIVE`
- `POLICY_EXPIRED`
- `RAIL_NOT_ALLOWED`
- `MERCHANT_NOT_ALLOWED`
- `RECIPIENT_NOT_ALLOWED`
- `MCC_NOT_ALLOWED`
- `TOO_MANY_TRANSACTIONS`
- `PER_TRANSACTION_LIMIT_EXCEEDED`
- `TOTAL_BUDGET_EXCEEDED`
- `APPROVAL_REQUIRED`
- `DUPLICATE_INTENT`
- `KILL_SWITCH_ACTIVE`

Reason codes make the denial demo crisp and testable.

## 8. Rail router

```ts
function selectRail(input: {
  sellerSupportsX402: boolean;
  sellerAcceptsCard: boolean;
  sellerHasRainPayoutRoute: boolean;
  amountMinor: bigint;
  isDigitalResource: boolean;
  requiresChargebackProtection: boolean;
}): "x402_monad" | "rain_card" | "rain_payment" {
  if (input.sellerSupportsX402 && input.isDigitalResource && !input.requiresChargebackProtection) {
    return "x402_monad";
  }
  if (input.sellerAcceptsCard) return "rain_card";
  if (input.sellerHasRainPayoutRoute) return "rain_payment";
  throw new Error("NO_SUPPORTED_PAYMENT_RAIL");
}
```

Use deterministic selection. The LLM can explain the route but must not choose an unsupported rail.

### Minimal onchain contract

Store hashes only:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract MissionAuditRegistry {
    event PolicyCommitted(
        bytes32 indexed missionId,
        bytes32 indexed policyHash,
        address indexed principal,
        uint64 expiresAt
    );

    event ReceiptCommitted(
        bytes32 indexed missionId,
        bytes32 indexed receiptHash,
        uint256 amountMinor,
        bytes32 rail
    );

    mapping(bytes32 => bytes32) public policyHashOf;

    function commitPolicy(
        bytes32 missionId,
        bytes32 policyHash,
        uint64 expiresAt
    ) external {
        require(policyHashOf[missionId] == bytes32(0), "already committed");
        policyHashOf[missionId] = policyHash;
        emit PolicyCommitted(missionId, policyHash, msg.sender, expiresAt);
    }

    function commitReceipt(
        bytes32 missionId,
        bytes32 receiptHash,
        uint256 amountMinor,
        bytes32 rail
    ) external {
        require(policyHashOf[missionId] != bytes32(0), "unknown mission");
        emit ReceiptCommitted(missionId, receiptHash, amountMinor, rail);
    }
}
```

This does not enforce Rain's offchain card authorization. It proves that the displayed policy/receipt existed unchanged. Rain remains the enforcement layer for Rain payments.

### x402 seller

Host one tiny paid endpoint, for example vendor-risk or price intelligence. Price it at `$0.001`. Return deterministic JSON so the demo never depends on another external dataset.

## 11. Webhooks and state

### Webhook handler rules

1. Read raw bytes before JSON parsing.
2. Verify sponsor-documented signature and timestamp.
3. Reject expired replay windows.
4. Insert event ID under a unique database constraint.
5. Return success for known duplicates.
6. Transition only through allowed state edges.
7. Store redacted payloads.
8. Publish a UI timeline event.

### Allowed state examples

- `submitted -> authorized`
- `submitted -> declined`
- `authorized -> settled`
- `authorized -> reversed`
- `authorized -> expired`

Reject `settled -> authorized` or other backwards transitions unless Rain documents them.

## 12. Security checklist

- [ ] Rain API key server-side only.
- [ ] Monad private key server-side only; use test wallet.
- [ ] No keys in logs, screenshots, browser bundle, or repository.
- [ ] No full card details sent to LLM or database.
- [ ] Rain-approved display method for sensitive card data.
- [ ] Raw-body webhook signature verification.
- [ ] Idempotency keys for every external mutation.
- [ ] Unique constraint for webhook event IDs.
- [ ] Deterministic policy validation after LLM output.
- [ ] Human approval for elevated spend.
- [ ] Global kill switch.
- [ ] Card expiry and post-task retirement.
- [ ] Maximum five agent steps.
- [ ] Request timeout and bounded retries.
- [ ] Private receipt data offchain; hash only onchain.
- [ ] Clear sandbox/testnet labels.
- [ ] No misleading claim that a simulated transaction is live.

## 13. Failure plan

| Failure | Behavior | Demo recovery |
|---|---|---|
| Rain API unavailable | Stop new Rain mutations; preserve intent | Switch to labeled simulation and replay recorded successful event |
| Monad RPC unavailable | Queue hash/tx; show pending | Use backup sponsor-approved RPC; retain Rain flow |
| x402 facilitator unavailable | Fail closed; do not expose resource | Replay recorded handshake plus transaction explorer link |
| Duplicate webhook | Acknowledge, no duplicate transition | Show idempotency event |
| LLM malformed plan | Reject schema; regenerate once | Use deterministic saved plan |
| Merchant out of scope | Deny before card creation | This is a feature demonstration |
| Rain authorization decline | Record reason/state; retire card | Show expected denial path |
| Browser/network failure | Preserve server state | Refresh mission by ID |

Record a clean 90-second backup video after first successful full run.

## 16. Pitch

### 15 seconds

“Agents can already decide what to buy, but payment authority is still all-or-nothing. RainRoute gives each task a bounded budget, uses x402 on Monad for machine services, and creates a Rain scoped card for ordinary merchants. The agent can transact anywhere, but it cannot escape the policy.”

### 60 seconds

“Today an AI agent either has no money or has a dangerously broad credential. RainRoute changes that. A business gives an agent a procurement task and a precise economic policy. The agent discovers and pays machine-native services through x402 on Monad, then uses a just-in-time Rain scoped card when the selected vendor only accepts cards. Rain enforces merchant, category, amount, frequency, and expiry controls. Monad records policy and receipt hashes and can supply agent identity and reputation. In our demo the approved purchase succeeds, an unrelated oversized purchase is blocked, and the card retires automatically. This turns autonomous commerce from ‘trust the model’ into enforceable, auditable authority.”

### Five-minute demo order

1. Problem: broad payment credentials are unsafe.
2. Enter mission and policy.
3. Show structured agent plan.
4. Show x402 payment and Monad explorer.
5. Show Rain scoped card issued.
6. Show allowed purchase.
7. Show blocked purchase and reason.
8. Show card retired and audit receipt.
9. End on enterprise expansion: travel, cloud, payroll, and procurement.
